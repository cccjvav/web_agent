# agent-host 服务入口：逐函数与初始化顺序

## 职责与依赖

源码 [index.js](index.js) 是 `npm start` 实际运行的入口，负责拼装 Express/HTTP/WebSocket；业务工具和模型逻辑留在其他模块。先读[本目录说明](README.md)再读本文。

依赖分三类：express/http/ws 建立传输层；config/store/tracker/eventBus 提供配置、持久化、用量和事件；API/MCP/OAuth 路由及 localControl/corsAllow 决定请求去哪里以及谁可访问。导入模块可能已有初始化副作用，不能只从第一个 function 开始看。

## 1. 顶层执行流程

1. require配置后立刻验证workspaceRoot是已存在目录；不合法打印错误退出1，不创建目录。
2. 验证通过才导入MCP/API/store等可能有副作用的模块。
3. `persistIdentity(store)`持久化身份，`tracker.startReporter()`建立上报生命周期。
4. 创建 UI/MCP 两个 Express app，按顺序挂中间件和路由。
5. 创建两个 HTTP server，只有 uiServer 调 `attachWss`。
6. 根据 `WEBAGENT_SKIP_WORKBENCH === '1'` 决定是否监听 UI；始终启动 MCP 监听。
7. 导出两个 app 和两个 server；但**require 本文件也会执行上面流程**，它不是没有副作用的纯工厂。

当前第1步已在加载MCP/API等业务模块和persistIdentity之前验证工作区，显式错误根不会因初始化身份而创建。配置/版本的产品清单读取不等于创建用户工作区；安装器允许缺省用户工作区首次创建是另一分支，不能套到显式错误路径。

## 2. 所有具名函数与内嵌回调

### securityHeaders(req,res,next)

F70（外部复审P2-11）：给每个响应设`X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`、`Content-Security-Policy: frame-ancestors 'none'`、`Referrer-Policy: no-referrer`后调用next。刻意收窄：本产品没有任何地方用iframe嵌入工作台（VS Code扩展渲染自己的webview HTML），故禁止被框住不影响现有功能；不设限制script-src的完整CSP，因为工作台从jsDelivr加载Monaco并有一段内联主题脚本，需先审定白名单与浏览器测试。静态资源也经过它（由applyCommon在express.static之前注册）。httpSmoke在工作台页面、两端/health与MCP 401上断言四个头及无x-powered-by，基线红。

### applyCommon(app,{mcp=false}={})

输入 Express app，不返回业务值，副作用是注册中间件。禁用 x-powered-by；第一个 `(req,res,next)` 回调给响应设 `Cache-Control:no-store` 后调用 next，接着注册securityHeaders；随后既有/probe-link传输保持原位置（本轮不复核探测专项），/api先验证本机与跨站边界；mcp模式先在/mcp前缀硬拒绝不允许的Origin，再挂CORS，对/mcp与/mcp/:secret（OPTIONS除外）用原认证函数验证，最后解析正文。允许的OPTIONS由CORS结束，不需凭据；不允许的Origin先403。OAuth JSON 64KiB，其余JSON仍20MiB（包括未命中有效认证路径的请求，不是全站先认证）；表单64KiB/最多32参数、extended=false。

顺序避免不允许Origin或有效路径上未认证的MCP先解析正文；即使合法密钥配畸形JSON，恶意Origin仍先403。早期401不读取JSON-RPC id，所以id=null。业务路由仍复验认证，后续拿到解析后的req.body。JSON 解析错误/超限可在业务路由前终止，由最后挂载的jsonErrors统一成JSON。no-store 是缓存指令，不是数据脱敏。

### jsonErrors(err,req,res,next)

F70第七批：两个app最后挂载的错误中间件。此前没有它，body-parser失败（畸形JSON、超限正文、字符集错误）由Express默认处理器回HTML错误页，含异常文本、绝对安装路径与完整调用栈——在认证之前、任意路径、经隧道都可触发（`POST /oauth/register`带`{bad`即可，已在真实主机复现）。现在保留解析器给出的4xx/5xx状态（非法值按500），按err.type映射固定英文说明，**从不回显err.message或栈**；`/mcp`路径回JSON-RPC形状（解析失败-32700，其余4xx为-32600、5xx为-32603，id为null），其他路径回`{error}`。5xx只在服务端console记录方法、路径与消息。已发出响应头时只结束响应。四个参数是Express识别错误中间件的方式，next不使用。

### mountHealth(app)

注册 GET `/health`。回调返回 `{ok:true, product, version}`；没有访问数据库、模型、PTY 或外网。路由本身不收凭据；它只证明该服务能响应基本请求，不能用来关闭端到端验收。

### mountWorkbench(app)

先挂 workbenchDir 静态资源，再挂兜底中间件。回调对于非 GET、保留路由前缀和具有文件扩展名的路径调用 next，让后续/默认处理继续；只对适合前端路由的路径发送 `index.html`。

这是单页应用的路由回退，不是“任何失败请求都返回首页”。静态资源找不到也不应被误当成完整 JS 页面。副作用是注册处理器；请求到来时才发送文件。

### attachWss(server)

输入 HTTP server，返回绑定其 `/ws` 的 WebSocketServer。

- `verifyClient({req})` 在握手时检查本机控制面与浏览器 Origin，布尔结果决定接受与否；不是 MCP OAuth 验证。
- connection 回调再次检查本机条件，失败时尝试 `ws.close(1008,'local only')` 并返回，关闭异常在此吞掉。
- 通过后交给 `eventBus.addWsClient(ws)`；返回 false 时不发送连接消息。注册是否成功、容量和后续清理须接着读 eventBus，不能凭本函数猜测无限连接。
- 已注册客户端收到 type=connected 的 JSON，包括时间、serverName、version；不是任务成功消息。

本入口只给 uiServer 调用一次；MCP server 的流式协议不是这个 WS。该函数不负责追踪每个工具任务的取消。

### listenOrExit(server, port, label)

先注册 error，再用 `server.listen(port, config.host)` 监听；不返回 Promise，不负责等待模型或浏览器就绪。

error 回调特别识别 EADDRINUSE，打印端口与 label 并 `process.exit(1)`；其他错误打印对象也退出 1。不是自动换端口继续，更不能认为另一个壳已经监听就等于当前壳成功。

## 3. 路由装配顺序与匿名监听回调

| app | 顺序 | 应读出的边界 |
|---|---|---|
| uiApp | 公共中间件 → health → `/api` 本机/跨站检查 → workbench 静态/兜底 → jsonErrors | UI 的 API 不是远程 MCP；静态页面可读不代表有调用权限 |
| mcpApp | 公共中间件（含早期Origin/CORS/认证及正文解析） → health → OAuth router → `/mcp` Origin 检查及 MCP router → `/api` 本机/跨站检查 → jsonErrors | OAuth 发现与 MCP 保留远程认证路径；本机控制面仍独立限制；任何解析/未捕获错误只回JSON，不泄露路径与栈 |

未 skip 时注册 uiServer 的 listening 回调，打印产品、UI/MCP 地址、bind 与工作区。这些日志可能含带密钥 MCP URL，分享前脱敏。skip 时只在顶层打印说明，不监听 3000；由 code-server 占用该端口。

mcpServer 的 listening 回调只打印监听信息。两个 listening 回调都不改变授权状态、不证明实际外部服务可用，也没有建立业务取消映射。

## 4. 正常链、失败链与验证

正常：launch 传入已存在工作区 → 创建 apps/servers → 监听成功 → 浏览器请求 health/静态页 → UI 请求经过检查到业务路由。

失败例：端口占用 → server 发 error → listenOrExit 的回调打印明确错误并退出 1；不是 UI 一直无响应后悄悄切端口。配置/磁盘读写错误还可能发生在监听之前，应查看启动输出。

```bat
npm test --prefix webagent-core/agent-host -- --filter=httpSmoke
npm test --prefix webagent-core/agent-host -- --filter=skipWorkbench
```

这两条只覆盖相应文件，不能替代全量；localControl/corsAllow 等还有专门测试。真实浏览器与双壳/进程退出按[人工清单](../../../review/CHECKLIST_WINDOWS.md)验收。本文不把健康探针或导出对象存在当作语义认证。

## 5. shutdown与stdio清理
shutdown用shuttingDown防重入，SIGTERM/SIGINT时停止externalClient全部连接/stdio并等待closed，8秒截止后退出1，正常清理退出0。不会保存/恢复审批或自动重启第三方进程；不是整个应用所有后台任务的事务式排空。stdio监督器另外处理宿主强杀，WindowsJob和POSIX进程组限制见受控工具与工作流详解。

### 生命线：插件启动的主机随VS Code退出（R6第一期）

[utils/lifeline.js](utils/lifeline.js)只在VS Code插件经`launch.js host`启动主机时生效；CMD/网页工作台启动不设这两个环境变量，控制台stdin永远不会让主机退出。

| 函数 | 作用与边界 |
|---|---|
| pidAlive(pid) | `process.kill(pid,0)`探测；EPERM视为仍存活（进程存在但无权发信号） |
| watchLifeline({env,stdin,onLost,intervalMs,isAlive}) | onLost必填。`WEBAGENT_LIFELINE=stdin`时监听stdin：内部`discard`丢弃数据，`onEnd`在end/close/error时触发“stdin-closed”——插件持有管道写端，扩展宿主以任何方式退出（含崩溃）时操作系统都会关闭它。`WEBAGENT_PARENT_PID`为合法正整数时每5秒（unref定时器）探测父进程，不在则“parent-exited”，覆盖管道句柄泄漏到其他进程、EOF迟迟不来的情况。`fire`保证onLost只调用一次并先`stop`全部监听；返回`{active,stop}`，非法PID与未设变量时active为false |

index.js在shutdown定义后调用watchLifeline，其`onLost(reason)`打印`[lifeline] …主机正在关闭（先停命令与隧道）`再调用shutdown，所以cloudflared/ngrok与命令作业经正常清理释放，而不是被强杀后留下孤儿。验证：hostLaunch.test.js第1节（单元）、第6节（真实主机关闭stdin后正常退出、日志含`[lifeline]`、未走强杀；去掉接线时该断言失败）、第7节（父进程消失后真实主机退出）。
