# stopProcess：停止旧隧道的逐函数与回调讲解

## 职责与调用关系

源码 [stopProcess.js](stopProcess.js) 导出一个 stopProcess，供隧道模块在停止/替换子进程时等待。调用方仍需管理隧道代次、URL 和状态，见[模块说明](README.md)。本函数不建立隧道、不校验公网可用性、不关闭浏览器。

## 主函数 stopProcess(proc, graceMs = 1500)

输入 Node ChildProcess 和宽限毫秒，返回 Promise；**resolve 表示观察到退出或已无待运行进程，发出 kill 信号不是 resolve 的充分条件**。无 proc、exitCode/signalCode 已非 null 时直接返回已完成的 Promise。

其余情况新建 Promise，闭包保留 proc、resolve/reject 与 force/deadline 计时器。默认约 1500ms 后升级强制信号，约 3000ms 未观察到退出就拒绝。graceMs 本身没有范围校验，调用者应传合理值；unref 的计时器不会单独让 Node 进程保持存活。

## 执行流程与每个回调

| 函数/回调 | 何时执行 | 做什么、为什么 |
|---|---|---|
| Promise 执行器 | stopProcess 调用时同步执行 | 先注册事件/定时器再发信号，避免先退出而漏掉事件 |
| cleanup() | 已观察到退出或最终超时 | 清 force/deadline，并移除本函数安装的 exit/error 监听；不清理其他模块的监听 |
| exited() | proc 的一次性 exit 事件，或 errored 判断无进程 | cleanup 后 resolve；不检查退出码为 0，因为这里只需要确认旧进程不再占用 |
| errored() | proc 的一次性 error 事件 | 仅当没有 pid 且未 killed 时按“未产生可运行进程”走 exited；其他 error 不能证明已经退出，继续等 |
| force 定时回调 | graceMs 后仍等待 | 尝试 proc.kill('SIGKILL')；发送异常被捕获，不据此宣称成功 |
| deadline 定时回调 | graceMs * 2 后仍等待 | cleanup 后 reject，提示拒绝启动替代进程；调用方不能忽略失败再并行开一个 |
| Windows killer 的 error 回调 | 启动 taskkill 失败等发出 error | 尝试 proc.kill('SIGTERM')；本函数不把 taskkill 进程退出状态作为旧 proc 已退出的证明 |

安装完监听和计时器后，平台分支如下：

- Windows 且有 pid：启动 `taskkill /pid <pid> /t /f`，隐藏窗口、忽略输出。这是针对该 PID 的进程树，不是结束系统所有 Node。
- 其他情况：调用 proc.kill('SIGTERM')。
- 最外层发送动作抛错：捕获但仍等真实退出或 deadline。不能只因为 kill 返回/抛错，就断言进程已经停止。

## 正常与失败例子

正常：旧隧道 proc 收到停止 → 发 exit → exited 清理监听/计时器 → Promise resolve → 调用者才准备下一代隧道。

失败：停止信号未能结束进程 → force 尝试升级 → 仍无 exit → deadline reject → 调用者应暴露失败、不启动替代。这里的“拒绝替代”错误不是网络不可用的等价表述，而是进程生命周期没有得到确认。

## R5首包：只读隧道归属记录，不是残留回收器

`processIdentity.js`与`tunnelRegistry.js`不调用kill/taskkill，不按名称/端口扫描全系统，不改变bridgeRunning、URL或stopTunnel。新启动的cloudflare quick/named及ngrok各接一次observeTunnel，异步元数据失败不能阻止正常Bridge启动，固定警告也不打印Token/路径。旧版无记录进程不会被认领；目前无清理按钮/API，所有报告cleanupAvailable/canCleanup恒为false。

### processIdentity.js

- **validPid**只接受1–2147483647整数；**sameIdentity**同时比pid/start/executable，不把PID相等视为同一进程。
- **linuxIdentity**只读指定PID的/proc/stat、exe和系统boot_id；start为boot_id加启动ticks，读取exe前后复查启动ticks，僵尸/消失归absent，权限/中途变化或其他失败为unknown。它不是持有pidfd的原子终止能力。
- **inspectProcesses**最多64个PID，去重；Linux异步读取，Windows以系统目录PowerShell -NoProfile/-NonInteractive查询指定Process对象的StartTime UTC ticks和MainModule.FileName，路径小写规范，固定UTF8输出；不读取命令行/环境。每批8秒/128KiB，宿主最多两个并发Windows查询，超限/失败降为unknown；不插入非数字参数，不请求提权。macOS等尚未实现，返回unknown，不能据此认定不存在。Windows读取是诊断辅助进程，不是任意命令执行接口，也未证明消除了PID查询竞争。

### tunnelRegistry.js

- **validIdentity/validRecord**校验版本、UUID、平台、固定provider、正整数PID、有限身份字符串和不同宿主/目标PID；内容始终是不可信磁盘线索，不是清理授权凭据。
- **classify**先核对目标：absent→exited，不可读→unknown，身份不同→identity-changed。目标匹配但宿主无法确认或其PID被复用→unknown；宿主确认消失才orphan-candidate，身份匹配且活着则按instanceId分active-current/active-other。所有状态仍不可自动清理。
- **createRegistry**默认共用当前OS用户home下`.webagent/tunnel-processes-v1`；测试通过代码参数注入临时baseDirectory/inspect/instanceId/ownerPid，CLI不允许传路径/PID。不同项目的活宿主被识别为active-other，不扫其他用户。
- **directory(create)**解析home/base的真实路径，逐级拒绝子目录符号链接；POSIX还检查归属UID及不可组/其他写；创建mode0700。Windows模式位不是ACL认证，未来终止操作不能只信这些文件。没有对同UID恶意篡改作认证保证。
- **readRecords**opendir最多处理32个目录项，多余标complete=false，不无限readdir；每个合法UUID.json只读最多12KiB+1，检查普通文件、链接数、lstat/fstat身份及POSIX文件权限，拒绝静态链接/超限/坏JSON并统计invalidRecords。不会删除坏记录/旧记录或打印其正文；扫描与写入并发时可能看到暂不完整记录。
- **scan/snapshot**只对记录内PID查询，snapshot共享一次在途扫描；返回固定provider/PID/状态/id，不暴露exe、时间标识、实例UUID或错误原文。缺目录为空且不创建目录；读取失败返回registry-unavailable/complete=false。complete只指这次有界记录扫描，并非全系统没有残留。
- **observe**接收已spawn的ChildProcess，不接收argv/Token，核对OS身份与实际可执行路径，拒绝cmd/bat包装器。每条随机UUID记录以wx/mode0600写入，无覆写；容量不足/查询不可用只返回未记录状态，不停止隧道。多个宿主并发登记不是跨进程严格容量事务，扫描超32仍明确不完整。退出回调**clear**只异步移除本次创建的记录；查询/写入期间退出也复查，不能迟到写入有效存活记录。异常宿主退出未收到该回调时保留记录供后续检查。
- **observeTunnel**为三个provider调用点提供失效隔离，只输出固定“归属记录不可用，检测可能不完整”警告。没有守护隧道或自动回收的新承诺；原stopProcess行为不变。

### 回归与未完成项

`tunnelRegistry.test.js`的**main**在临时目录验证状态分类、PID/路径变化、权限未知、共享扫描、记录白名单且无Token、32项/12KiB边界、坏文件/链接、错误脱敏及迟到exit；实际OS读取自身和另一个存活Node，检测不得发信号。`tunnelOwnerFixture.js`只由测试fork，在临时目录登记自己的Node子进程并通过IPC报告；测试强杀夹具宿主后，必须报告orphan-candidate且子进程和另一个存活进程均不被杀。夹具子进程凭私有stop文件自行退出并有60秒兜底；正常路径观察退出后删临时目录，失败时保留stop文件，不对未知PID补杀。Windows/Linux CI测试是受控Node夹具，不是真实Cloudflare/ngrok长挂或桌面验收。

`tunnelLifecycle.test.js`另用observeTunnel spy检查quick/named/ngrok每个spawn恰好接一次，不改变原启动/替换/取消/退出断言。下一批仍需稳定进程句柄/归属可信度/清理前复核、有限预览和本机明确确认、结果逐项核验；不能把orphan-candidate直接接taskkill，更不能复用会关闭当前Bridge的stopTunnel。

命名辅助补充：linuxIdentity内部**readStat**两次读取同一指定PID的stat，第二次只核对启动ticks；Windows Promise内**unknown**把整批降为unknown而不传播原始错误。测试main中的**live**仅包装合成identity为alive，用于可控分类矩阵，不替代真实OS查询。
