# 产品测试运行器：没有导出函数也要读懂执行流程

## 职责与入口

源码 [run-tests.js](run-tests.js) 由 `npm test` 启动，使用 Node 自带模块顺序运行 tests 目录文件，不使用 Jest/Mocha。它主要是顶层流程与数组回调；不要因为没有 function 声明就漏掉讲解。[脚本 README](README.md)说明归属，[Conda 说明](../../../Conda环境说明.md)给出 CMD 实际命令。

## 按源码顺序解释

1. **定位与依赖检查**：`root` 相对 `__dirname` 指向 agent-host，`testsDir` 指向 tests，不依赖用户从哪层调用 npm。不存在 `node_modules/express` 就提示安装并退出 2；这只是启动前置检查，不证明所有开发依赖完整。
2. **preferred**：列出必须存在且优先执行的测试文件。某个必需文件被删不能因目录扫描变少而假绿。
3. **found/extra/missing**：readdirSync 后，第一个 filter 回调只保留 `.test.js` 后缀；extra 的 filter 选出不在 preferred 的文件并排序；missing 的 filter 找 preferred 中不在磁盘清单的文件。都是文件名级判断，不执行测试。
4. **参数循环**：接受非空 `--filter=子串`，其他参数退出 2；比较区分大小写，不是正则。多次传 filter 时后面的值覆盖前面，不会自动做并集。
5. **missing 检查**：存在缺失项退出 1；即使设置 filter，也不能借它绕过 mandatory 文件丢失。
6. **files filter 回调**：把 preferred+extra 合并，未指定 filter 就全选，否则 `includes(filter)` 做文件名包含判断。零匹配退出 2，不打印“0 tests passed”。
7. **超时**：`WEBAGENT_TEST_TIMEOUT_MS` 默认 120000，Number 转换后必须是 1000–600000 范围内整数，否则退出 2。这个预算按每个文件计，不是整套测试总时限。
8. **逐文件执行**：spawnSync 使用 `process.execPath`，所以子测试与 runner 用同一 Node；参数为测试文件绝对路径，cwd 固定 agent-host，stdio 继承，timeout 为上一步值。环境默认继承，不替你激活 Conda。
9. **单文件结果**：有 spawn error 就打印；r.status 为 null 时按 1 处理（如超时/信号退出），否则用实际状态；仅 code===0 为成功。记录 `{file,ok,code}`，失败数量累加，但继续执行后续文件。
10. **汇总**：遍历 results 打印各文件 PASS/FAIL。只要 failed 非 0，打印失败占比并退出 1；全通过打印文件数并自然结束 0。没有计算断言数、行覆盖率或语义认证百分比。

## 为什么这样设计

按文件分进程减少模块缓存/全局状态串扰；同步顺序执行让输出易读，但整体时长随测试增长。每个文件自己负责清理它启动的服务和临时文件；runner 超时失败不保证其所有孙进程已被自动清理。

Windows 上 `run-tests.cmd` 会先检查 Node、必要时安装依赖，最后 pause；实际测试语义仍是此 runner。文档测试需要开发依赖，不要用启动器的生产依赖安装代替 `npm ci --include=dev`。

## 正常/失败用法与验证

仓库根执行：

```bat
npm test --prefix webagent-core/agent-host
npm test --prefix webagent-core/agent-host -- --filter=testRunner
```

第一条是交付用的全量；第二条定位 runner 自身回归，不是“全部产品测试通过”。`--filter=不存在的名字` 应退出 2，而一个实际测试断言失败应让整套最终退出 1。

观察 `testRunner.test.js` 对参数、缺文件和超时等场景的实际断言，区分“测试脚本能跑”与“业务确实符合要求”。真实 Windows/浏览器/手机的剩余工作仍看[验收清单](../../../review/CHECKLIST_WINDOWS.md)。
