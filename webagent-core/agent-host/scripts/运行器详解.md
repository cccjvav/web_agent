# 产品测试运行器：入口、汇总与诊断流程

## 职责与入口

源码 [run-tests.js](run-tests.js) 由 `npm test` 启动，使用 Node 自带模块顺序运行 tests 目录文件，不使用 Jest/Mocha。它以顶层流程/数组回调为主，另有lifecycleSummary具名辅助；不能只查导出函数而漏掉实际入口和诊断流程。[脚本 README](README.md)说明归属，[Conda 说明](../../../docs/guides/Conda环境说明.md)给出 CMD 实际命令。

## 按源码顺序解释

1. **定位与依赖检查**：`root` 相对 `__dirname` 指向 agent-host，`testsDir` 指向 tests，不依赖用户从哪层调用 npm。missingDependencies用filter检查express/Acorn的本地package.json；缺任一项就打印具体缺失项及`npm ci --include=dev --no-audit --no-fund`并退出2，不自动安装。这只是关键入口存在性检查，不证明完整依赖树/文件完整性。
2. **preferred**：列出必须存在且优先执行的测试文件。某个必需文件被删不能因目录扫描变少而假绿。
3. **found/extra/missing**：readdirSync 后，第一个 filter 回调只保留 `.test.js` 后缀；extra 的 filter 选出不在 preferred 的文件并排序；missing 的 filter 找 preferred 中不在磁盘清单的文件。都是文件名级判断，不执行测试。
4. **参数循环**：接受非空 `--filter=子串`，其他参数退出 2；比较区分大小写，不是正则。多次传 filter 时后面的值覆盖前面，不会自动做并集。
5. **missing 检查**：存在缺失项退出 1；即使设置 filter，也不能借它绕过 mandatory 文件丢失。
6. **files filter 回调**：把 preferred+extra 合并，未指定 filter 就全选，否则 `includes(filter)` 做文件名包含判断。零匹配退出 2，不打印“0 tests passed”。
7. **超时**：`WEBAGENT_TEST_TIMEOUT_MS` 默认 120000，Number 转换后必须是 1000–600000 范围内整数，否则退出 2。这个预算按每个文件计，不是整套测试总时限。
8. **逐文件执行**：spawnSync 使用 `process.execPath`，所以子测试与 runner 用同一 Node；参数为测试文件绝对路径，cwd 固定 agent-host，本地stdio继承，CI捕获后回放，timeout 为上一步值。环境默认继承，不替你激活 Conda。
9. **单文件结果**：有 spawn error 就打印；r.status 为 null 时按 1 处理（如超时/信号退出），否则用实际状态；仅 code===0 为成功。记录 `{file,ok,code}`，失败数量累加，但继续执行后续文件。
10. **汇总**：遍历 results 打印各文件 PASS/FAIL。只要 failed 非 0，打印失败占比并退出 1；全通过打印文件数并自然结束 0。没有计算断言数、行覆盖率或语义认证百分比。

## 为什么这样设计

按文件分进程减少模块缓存/全局状态串扰；同步顺序执行让输出易读，但整体时长随测试增长。每个文件自己负责清理它启动的服务和临时文件；runner 超时失败不保证其所有孙进程已被自动清理。

Windows 上 `run-tests.cmd` 会先检查 Node、必要时安装依赖，最后 pause；实际测试语义仍是此 runner。文档测试需要开发依赖，不要用启动器的生产依赖安装代替 `npm ci --include=dev`。

## 正常/失败用法与验证

仓库根执行：

```bat
npm test --prefix webagent-core/agent-host
npm test --prefix webagent-core/agent-host -- --filter=testRunner
```

第一条是交付用的全量；第二条定位 runner 自身回归，不是“全部产品测试通过”。`--filter=不存在的名字` 应退出 2，而一个实际测试断言失败应让整套最终退出 1。

观察 `testRunner.test.js` 对筛选、未知参数、无匹配、非法超时参数及缺express/Acorn的实际断言（不把非法超时参数当真实长时进程超时），区分“测试脚本能跑”与“业务确实符合要求”。真实 Windows/浏览器/手机的剩余工作仍看[验收清单](../../../review/CHECKLIST_WINDOWS.md)。

CI环境GITHUB_ACTIONS=true时捕获单文件stdout/stderr（最多16MiB），结束后原样打印，失败另输出转义前最多4500字符的GitHub error annotation，转义百分号与换行便于Checks定位；本机仍inherit实时输出，超时/非零语义不变。

新增依赖回归把runner复制到临时scripts目录，分别不建依赖、只建express入口，真实启动子进程断言退出2/缺Acorn/安装指引及未开始PASS；不移动真实checkout依赖。finally删除临时树。

R4新增固定元数据：每个文件启动前输出[test-context]（文件名/Node版本/平台/架构/原timeoutMs）；结束后[test-result]补单调elapsedMs、status/signal/errorCode和捕获输出字节数，inherit模式字节数为null而非假0。不含cwd/绝对路径或环境变量。失败annotation先带此元数据和下述生命周期摘要，再带既有有界错误片段；这些完整日志原本就可能含测试夹具输出，不将元数据字段不含正文夸成整个日志已脱敏。异常退出/超时仍失败，没改preferred顺序、默认120秒、重跑次数或退出码。

## tunnel-residue.js：独立只读残留检测入口

这是本地诊断脚本，不属于run-tests的preferred测试，也不是MCP工具。仓库根CMD执行：

```bat
node webagent-core\agent-host\scripts\tunnel-residue.js
```

仅接受零参数；`--cleanup`、任意PID/路径都退出2，不做任何检查或清理。snapshot完成后打印固定JSON，complete为true退出0、false退出1；0只表示完成这次有限登记扫描，不代表全机无残留。异常回调只输出固定提示。readOnly恒true、cleanupAvailable及逐项canCleanup恒false，orphan-candidate只是待确认线索；CLI自身是新实例，正在运行的其他宿主列active-other。读取已有当前用户home记录，不创建目录、不删除记录、不启动隧道、不杀进程；Windows会启动有界只读PowerShell身份查询，不读取argv/Token。不支持旧版无记录进程认领，不能替代下述独立本机确认回收入口。详见[tunnel归属说明](../src/tunnel/停止进程详解.md)。

R5续包的逐项报告增加integrity（unverified/os-user-protected）；表示本次记录完整性校验，不是可清理授权。CLI仍不接受cleanup/PID/路径参数。


## tunnel-cleanup.js：Windows本机交互确认入口

在仓库或安装根目录的本机交互CMD执行（Node接受此路径分隔符）：

```bat
node webagent-core/agent-host/scripts/tunnel-cleanup.js
```

**main**只接受零参数、win32及stdin/stdout均为TTY；PID/路径/--yes参数、管道喂RECYCLE或非Windows退出2，不启动执行辅助。显示原生预览/跳过计数，没有candidate就关闭租约退出。readline只接受精确RECYCLE，其他回答/Ctrl+C/租约到期取消，finally关闭终端/租约。确认后逐项显示结果；failed/unconfirmed/not-started/owner-unknown/inaccessible退出1，0不代表所有项已清理。确认后断连/失败提示结果未知，不要重放。

TTY+输入是本机交互门槛，不是防自动化的人类身份认证；获授权的本机代码/桌面自动化仍可能输入。无HTTP/MCP清理接口、自动重试、提权或按名称全杀。普通tunnel-residue.js依旧只读且拒绝--cleanup；图形按钮未实现。详见[tunnel句柄说明](../src/tunnel/停止进程详解.md)。


## R4：保留被首尾截断遗漏的生命周期中段

**lifecycleSummary(stderr)** 仅处理失败文件已捕获的stderr，最多扫描前16MiB；用整行固定前缀process lifecycle / tunnel helper匹配，不读取日志文件或新增进程。每行JSON最长4096字符，坏JSON/数组/无效kind、operation或event丢弃；只重建固定枚举、整数/布尔字段，绝不展开原对象或保留command/path/env/原输出。command/search的PID、threadId只作为测试内关联数字，tunnel字段仍由有限操作名/调用序号表示；数值和枚举不是权限或人类身份凭据。

保留最后最多6条且JSON总长≤1800字符的有效记录；超过则淘汰最早记录。它不是完整时间线，不保证每个并发进程都覆盖，原始日志仍应优先取回；日志行也可能由程序伪造，摘要不能认证来源或自动决定重试/终止。

失败GitHub annotation在[test-result]元数据之后优先插入 `[lifecycle-summary]`，再附原有错误首尾片段，整条转义前仍≤4500字符。此改动修复“有阶段日志但被首1600/尾1000窗口截掉”的可观察性缺口，不证明历史echo超时根因。原16MiB捕获、120秒默认文件预算、执行顺序、失败退出码、无重跑策略均不变。只有新增摘要字段经过白名单，完整回放与原首尾片段仍可能包含测试输出，不能称整个CI日志已脱敏。

`testRunner.test.js`在隔离临时runner里生成失败夹具，将timeout和辅助callback放进大量首尾填充之间，先红测确认旧annotation漏掉阶段，再验证修订保留timeout/无输出/ready布尔值。额外含12条事件、坏JSON、超4096字符行、恶意字段/枚举/字段类型，验证最后6条/1800字符和敏感哨兵不进入摘要；仍必须退出1，不能把诊断成功误判测试成功。
