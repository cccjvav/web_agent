# 可复用的维护经验

本文只保留仍适用的维护方法；历史施工与失败证据在阶段记录及review中，不再在这里维护第二份未完成清单。当前任务从[CONTEXT](../CONTEXT.md)进入。

## 恢复会话与保护工作树

先检查实际工作树、当前分支、HEAD和远端提交，不根据“出现很多修改”就判断文件丢失。本会话曾出现工作树已是新版本而Git元数据仍在旧基点的情况，这与真实内容回退不同。

远端能恢复已推送提交，但不能恢复未提交、未推送或被忽略的数据。不要把origin称为全部状态的可靠备份，更不要在核对前执行reset --hard。先保存差异和必要的本地数据，取得远端后比较树；只在确认没有丢失本地工作的方案下修复元数据。当前会话必须留在Arena指定分支。

每个已验证批次及时推送，记录精确提交、CI run及未完成工作；不能拿旧提交绿灯覆盖新提交。

## 测试证据分层

测试文件存在不是通过证据。源码字符串断言、VM/DOM夹具、真实HTTP/子进程、Chromium、真实Windows桌面窗口是不同层级；报告只写实际执行的层级。外部报告和参考截图也要先与当前实现交叉核对，不能直接当施工任务。

`npm test | tail`可能只返回tail的退出码。保存日志后检查npm真实退出码，或使用支持pipefail的shell并启用它。失败文件、平台和后续修复要记录，不把重跑成功写成从未失败。

Windows Node矩阵和安装器编译不能证明code-server窗口、VS Code终端或真实手机网络可用。用户明确关闭的协作说明不应换名重开，也不能变造为真机证据。

## 编辑、取消与并发

保存要区分编辑缓冲区、提交快照与磁盘版本；成功响应只能确认提交的快照，不能抹掉保存期间的新编辑。切换标签页后，旧响应不能污染新激活文件。冲突后保留用户内容，先核对再操作。

hash用于版本冲突检测，不是授权、锁或回滚票据。拿到新的currentHash不能直接把旧补丁重放。取消可能发生在副作用之后；unknown不等于未执行，不自动换请求键或重放。进程树回收也不是文件/网络权限沙箱。

## 截图与模型输出

当前截图辅助由本机Chat与MCP共用：Chat向声明vision的模型传image_url部件，MCP可返回image内容，不能再写“Bridge恒为text”。图片base64不经eventBus广播。

当前路径规则允许工作区和产品computer-use目录，支持PNG/JPEG并设置6MiB检查；该目录例外不是严格工作区隔离，也不是截图隐私认证。命令stdout路径识别仍可能触发附图，需保留安全说明；不要把图片塞进会被裁切的纯文本结果冒充完整多模态输入。实现见[截图辅助](../../webagent-core/agent-host/src/agent/computerUse.js)。

## 文档不是更新记录的堆叠

原句错误就改原句，不在后面追加相反“补充”。失去用途的重复方案和旧统计可以删除，引用与站点路由同时处理；授权来源、失败证据与未解决发现先核对归属再决定删除。

逐文件/逐函数解释保留关键分支、输入输出、副作用和错误边界。自动符号、行号、清单hash及链接校验只负责定位，不能替代语义审查。未完整阅读的源码、未复核的正文以及真实平台未执行项分别注明。

生成器从真实文件集合发现新增内容；生成物要可重复，换行归一要兼容Windows。发行文档包含源码快照时，不把测试夹具和有效凭据一并分发。规范唯一入口是[文档维护规则](documentation.md)。

## 画像与记忆的输入/输出预算

读取有上限却允许无限写入，会让自身保存的数据下一次不可读；校验预算须包含序列化转义、默认字段、日期标题及时间戳。派生文件应在第一份发布前完成可预测的格式化/预算检查，但顺序rename仍不是多文件事务。append前不能用existsSync把悬空链接当作新文件，需lstat识别并拒绝；这不替代与恶意同用户进程的竞态隔离。R1回归和限制见[阶段10](../stages/s10-upstream-adoption.md)。

## 异步状态发布与写后刷新

### 场景：模型保存已确认，但GET失败或旧读取迟到
- **标签**：`#并发` / `#调试`
- **创建日期**：2026-09-17
- **现象**：错误JSON可被当状态发布；隐藏select保留旧值却显示新模型；点击选择在HTTP拒绝前就成为Chat输入。
- **根因分析**：fetch完成不代表HTTP/业务成功，Abort不代替响应序号屏障；可消费控件的乐观更新与服务端确认混用。
- **解决方案**：校验核心响应后发布；在headers/body两个await后核对请求序号；保存与刷新分开报告，确认前恢复消费控件为最后确认值，不自动重放未知写入。
- **核心经验**：读取竞争要定义谁能发布；写入确认不能被后续读取失败抹去，也不能把旧快照当成新确认。局部schema/DOM渲染不是完整事务或身份认证。
- **关联阶段**：→ stages/s10-upstream-adoption.md（第31组）

### 场景：添加Provider不能用脱敏读模型表重建配置
- **标签**：`#存储` / `#安全`
- **创建日期**：2026-09-17
- **现象**：旧Add用builtin+发现结果替换整表；若简单在前端拼旧表，又会丢失或写回掩码Key。
- **根因分析**：展示快照不具备持久化完整数据，添加与替换语义没有分开。
- **解决方案**：服务端基于磁盘仅追加、整批冲突拒绝；精确Endpoint/模型ID生成稳定ID；单独确认added，发现/手动登记/保存分开，未知效果不重放。
- **核心经验**：脱敏接口不可逆，不能当更新底稿；创建成功既需业务确认，也需确认服务器理解本次操作合同。
- **关联阶段**：→ stages/s10-upstream-adoption.md（第32组）。

### 场景：审批执行异常不等于没有效果，审阅旧按钮也不是新授权
- **标签**：`#审批` / `#并发` / `#调试`
- **创建日期**：2026-09-17
- **现象**：真实写盘后的事件异常被记普通失败；handler尚running却获succeeded；迟到详情覆盖新审阅，旧按钮可脱离展示继续调用。
- **根因分析**：异常代码被当执行阶段证明，非失败被当完成，异步控件没有绑定所展示请求。
- **解决方案**：显式区分调用前/已派发，已派发写入异常保守unknown；非终态不消费为成功。审阅ID/代次绑定，先失效旧控件再await、POST前消费，取消保留已确认效果，不自动重放。
- **核心经验**：先用真实磁盘效果复现，不凭假handler推定底层行为；保守unknown也要保留已知调用前拒绝。新增浏览器函数应写入既有主说明归属，不因附近测试文档提到就误以为完成同步。
- **关联阶段**：→ stages/s10-upstream-adoption.md（第33组）。

### 场景：界面把“请求已发出”当“操作已成功”
- **标签**：`#结果消费` / `#回归` / `#调试`
- **创建日期**：2026-09-18
- **现象**：第41–43组连续发现同类缺陷——经典密钥轮换HTTP500仍提示已重置；经典启动在途可重复POST；原生`resetSecret`发空体且完全不看status/json。
- **根因分析**：`fetch`/`requestJson`只要resolved就被当成功；没有绑定字段，过期页面可以写别的主机；写确认与后续读取混为一谈。
- **解决方案**：统一合同——页内单飞+动作代次、捕获绑定与草稿快照、严格回包（HTTP+`success`严格布尔+业务字段）、409拒绝与未知分开、写确认后读取失败保留确认、不自动重试、独立aria-live结果区。先写红测复现假成功，再修实现。
- **核心经验**：`success:'true'`这类字符串真值会骗过`!data.success`，必须`=== true`；测试夹具里的简写方法（`show(){}`）会被文档守卫当成未说明的命名函数，改用箭头属性。
- **关联阶段**：→ stages/s10-upstream-adoption.md（第41–43组）。

### 场景：沙箱浅克隆让HEAD看起来回到旧提交
- **标签**：`#交接` / `#Git` / `#环境`
- **创建日期**：2026-09-18
- **现象**：`git log -1`显示很旧的提交，但工作树文件是最新；`git rev-parse origin/<工作分支>`直接失败。
- **根因分析**：沙箱是浅克隆（`.git/shallow`存在，本地仅33个提交），且fetch refspec只有`+refs/heads/main:refs/remotes/origin/main`，工作分支没有远端跟踪引用。
- **解决方案**：用`git ls-remote origin refs/heads/<branch>`核对远端；需要对照时`git fetch origin <branch>`后用`FETCH_HEAD`；确认工作树等于远端（`git diff --quiet FETCH_HEAD --`）后才`update-ref`/`read-tree`，动手前先`git diff --binary HEAD`备份。
- **核心经验**：不要用`reset --hard`/`clean -fd`/整树覆盖“修”这种错配；本地历史被截断，`git log`不是完整项目史。
- **关联阶段**：→ stages/s10-upstream-adoption.md（第44组、全仓检查报告P3-B）。

### 场景：管理文档沿用上一批数字导致自相矛盾
- **标签**：`#项目管理` / `#证据`
- **创建日期**：2026-09-18
- **现象**：F43写“局部30、待103口径不变”，同句又说本批把两篇改为局部；CONTEXT基线行仍写82测试文件/246源码。
- **根因分析**：从上一批文案复制数字，没有重算。
- **解决方案**：每批收尾用命令重算（`npm test`尾行、`check-docs`输出、清单状态`uniq -c`）再写文档；数字与同批事实冲突时以命令输出为准并当场更正。
- **核心经验**：管理文档里的数字也是证据，过期数字会把接手助手引向错误结论。
- **关联阶段**：→ stages/s10-upstream-adoption.md（第44组）。
