# 项目核心经验

## 编辑器异步保存

保存必须区分当前缓冲区、已提交快照与磁盘版本hash。成功响应只能确认提交的快照，不能清除保存期间的新编辑；切tab不能让响应污染新激活文件。每文件模型需复用并在关闭时释放，避免丢撤销历史和泄漏。

## 审计交叉验证（2026-09-11）

- 外部报告的文件名、计数和建议不是事实：先定位真实实现和测试，再区分新增、重复、部分成立或误报。
- 源码字符串断言不证明模块能启动；补实际模块执行与HTTP/WS握手。DOM fixture也不能冒充浏览器E2E。
- 全绿只验收本批，Windows/VS Code及未修生命周期仍保留F编号。
- 字符截断不能代替读取前字节预算；原子写需验证mode与失败清理。

## 沙箱与会话工程

### 场景：Arena 沙箱在回合内/回合间被回收，工作树回滚到旧提交
- **标签**：`#工程` `#会话恢复`
- **创建日期**：2026-09-07
- **现象**：bash 调用之间工作树整体回退（曾回滚掉一次已完成的 FF 合并）；被移动过的文件留下陈旧未跟踪副本；长会话记忆被压缩后细节丢失。
- **根因分析**：沙箱文件系统按快照持久化，回收点不可控；origin 是唯一可靠的持久存储。
- **解决方案**：① 每个绿批次立即 commit+push（小步提交，不攒大包）；② 仓库内维护「活文档」恢复锚点（`review/REPORT_SHUNCODE_S1.md` 施工进度表 + 本 manager/ 体系），每批随代码一起提交；③ 恢复时用 `git ls-remote --heads origin` + 显式 refspec fetch + `reset --hard`，**不信任** `git branch -r`；④ fetch+判定+读取写进同一条自包含 bash 调用，减少回收窗口。
- **核心经验**：把「恢复所需的全部状态」放进 git 并即时推送——远端 tip + 一份活进度表 = 可无损续作。
- **关联阶段**：→ stages/s1-handoff.md

### 场景：`npm test | tail` 显示通过，实际 1/30 失败仍被提交
- **标签**：`#测试` `#shell`
- **创建日期**：2026-09-07
- **现象**：管道后 `&&` 链继续执行并 commit+push 了带失败测试的批次（失败文件随后 3 次重跑不可复现，判定偶发）。
- **根因分析**：管道退出码 = 最后一个命令（tail）的退出码，npm test 的非零码被吞。
- **解决方案**：`npm test > /tmp/x.log 2>&1; echo "exit=$?"` 再判定；或 `set -o pipefail`。提交前必须看到显式 `exit=0`。
- **核心经验**：任何「绿了才提交」的判定，都必须校验真实退出码，不看管道尾部文字。
- **关联阶段**：→ stages/s1-handoff.md

## 视觉管线（本机 Chat）

### 场景：让模型「看到」截图的通路选择
- **标签**：`#架构` `#多模态`
- **创建日期**：2026-09-07
- **现象**：截图 base64 塞进工具结果文本会在 ~65537 字符处被截断，模型收到半张图。
- **根因分析**：文本通道有长度上限且模型不按图片解码文本里的 base64。
- **解决方案**：图片必须走 OpenAI 兼容多模态 `image_url`（data URL）部件，在 agent 层（`src/agent/computerUse.js` + `openai.js` 工具循环）拼装；共享 MCP 工具层不动，Bridge 恒 `{type:'text'}`。
- **核心经验**：图片进模型只有 `image_url` 一条正路；能力增强放在独占层（agent），不动多方共用的契约层（MCP）。
- **关联阶段**：→ stages/s1-handoff.md

## UI 对齐

### 场景：照参考截图列「差距清单」后直接开工
- **标签**：`#UI` `#流程`
- **创建日期**：2026-09-07
- **现象**：S4 按 ShunCode 截图列了 5 项差距，侦察代码发现其中 2 项（失败卡红框、Bridge 折叠组）早已实现，差点重做。
- **根因分析**：截图是「对方有什么」，不是「我们缺什么」；目视清单没和现有代码核对。
- **解决方案**：差距清单先逐条 grep 现有实现（样式类名/组件/markup），确认缺失才进开发清单；已实现的直接划掉并记录。
- **核心经验**：参考图 → 差距清单 → **代码核对** → 开发清单，三步不可并两步。
- **关联阶段**：→ stages/s4-terminal.md

## 文档与 README 工程

### 场景：README 里的行号引用悄悄漂移
- **标签**：`#文档` `#工程`
- **创建日期**：2026-09-07
- **现象**：workbench/README 的 index.html 区段行号整体过期约 8 行（在本次改动之前就已漂移）；settings.js 条目标 L73 实为 L83。
- **根因分析**：HTML/JS 频繁增删，行号引用无人校，也没有（也不该有）测试锁行号。
- **解决方案**：凡改动被行号引用的文件，用 grep 量出各 landmark 实际起止行，整段重写引用，随同一提交落盘。
- **核心经验**：行号引用是必须当场偿还的文档债——动了文件就按磁盘实测校正整段，不欠到下一轮。
- **关联阶段**：→ stages/s2-shell.md

## 元管理

### 场景：元管理回路落地（项目管家 v12→v13，首条『技能进化』）
- **标签**：`#skill` `#元管理`
- **创建日期**：2026-09-08
- **现象**：对照第三方 PM-skill 评审（优点 5＝REVIEWS 复盘技能本身）核查自家 v12：复盘对象只有阶段/任务，技能原文无修订通道（仓内副本明定只读），经验改了代码与文档却从未改规则本身。
- **根因分析**：收工仪式缺「机制自我复盘」一问；只读副本规则把进化通道一并堵死。
- **解决方案**：v13 收工仪式加第 5 条元复盘 + 阶段模板复盘清单元复盘勾选 + 触发器（阶段关闭/任一 P1 解决）+ 修订只走原文升版本后覆盖副本；本条即首条『技能进化』记录。
- **核心经验**：管理机制必须把自己列为复盘对象，否则教训停在文档层、永远到不了规则层；「只读副本」要留唯一修订通道，否则只读=冻结。
- **关联阶段**：→ stages/s6-multi-agent-board.md
