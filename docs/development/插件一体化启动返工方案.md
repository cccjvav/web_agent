## 1. 用户诉求

R8记录末节提出：插件启动步骤太多；Bridge启动埋在“智能体自定义设置→Bridge页”，和侧栏权限卡片割裂；期望在插件侧栏点一下就启动主机和相关服务。

**用户2026-09-25澄清：** 不是要删除网页工作台，而是**使用VS Code插件版时不应该还依赖网页工作台**。网页工作台继续作为独立的使用方式保留和维护；插件版要能独立完成启动、设置、Bridge和审批。R8记录原文中“网页工作台……可去掉”的写法以这次澄清为准，记录本身作为历史证据不改。

## 2. 现状事实（按源码核对）

**今天的启动链。** 用户先在CMD运行`run-webagent.cmd`，再由`installer/launch.js classic`启动`agent-host/src/index.js`。主机开两个端口：3000给网页工作台（`WORKBENCH_PORT`），48271给`/api`、`/mcp`和`/ws`（`AGENT_HOST_PORT`）。插件自己**不启动主机**，只按设置`webagent.agentHostUrl`（默认48271）去连接；主机的工作区和VS Code打开的文件夹不一致时，状态栏显示“工作区不一致”。

**插件已有的能力**（`webagent-core/extension/extension.js`，约800行）：

- 活动栏“Web Agent”下有两个视图。
  - **Chat & Agent**：流式调用`/api/chat`。
  - **Bridge 模式 (远程指挥台)**：显示MCP地址，有**启动 Bridge / 停止 / 复制提示词 / 重置密钥**按钮，另有工作模式切换、四项权限、任务与日志。
- Chat参与者`@webagent`、PTY终端执行、草稿差异预览，以及状态栏。

**更正R8中的一处观察。** R8第5步和第5条反馈所说的“侧栏只有模式与权限”，指的是**网页工作台**的侧栏卡片。VS Code插件的“Bridge 模式”视图其实已经有启动按钮，只是隧道写死为Cloudflare Quick Tunnel（`tunnelProvider:'cloudflare'`），而且主机必须已经由CMD启动。所以插件版今天依赖网页工作台（和CMD）的地方有三处：

1. **主机只能在插件外启动**；
2. **模型与Bridge高级设置只在网页工作台里**；
3. **本机审批入口只在网页工作台里**。

**插件版还缺、只有网页工作台才有的功能**：

| 功能 | 主机接口 | 插件版怎么补 |
|---|---|---|
| 文件树与Monaco编辑器 | `/api/files/*` | 不需要，VS Code本身就有 |
| 网页Chat | `/api/chat` | 插件Chat视图已有 |
| **模型与API Provider**（新增/探测/切换） | `POST /api/models`、`/api/providers/probe` | **必须补**：没有它，插件Chat无模型可用（R8的9.2正是因此未执行） |
| Bridge高级：隧道选择（Quick/Named/ngrok）、域名/Token、客户端提示、重置MCP地址、OAuth设备配对 | `/api/bridge/*` | 补 |
| **待批与已执行请求**（外部请求、固定工作流的本机批准） | `/api/operations/*`、`/api/workflows/*` | **必须补**：这是本机审批入口 |
| 主机身份与能力诊断、连接核对 | `/api/diagnostics`、`/api/connection-checks` | 补（排障要用） |
| 跨文件检查点恢复 | `/api/checkpoints/*` | 补 |
| 环境偏好、技术栈、智能体、指令、提示、技能 | `/api/customizations`、`/api/skills`、`/api/profile/detect` | 补（这些写入工作区的`.webagent`） |
| stdio MCP / 外部MCP服务器 | `/api/external/*` | 待决定（第7节D4） |
| 多模型博弈 | `/api/consensus/run` | 待决定（D4） |
| 探针链接 | `/api/probe/*` | 探针暂停中，另一助手负责，本方案不动 |

**可以直接复用的基础：**

- 主机已支持`WEBAGENT_SKIP_WORKBENCH=1`，即不开3000端口的纯主机模式（原本给code-server用）。
- `launch.js`已有依赖准备，带期限和取消（`ensureDependencies`/`preparation.js`），还有工作区解析。
- 插件已有“扩展进程代理请求、webview不直接访问主机”的模式（`requestJson`加`postMessage`）。主机的`/api`只接受本机回环，并拒绝跨站Origin，这个安全边界保持不变。
- 所有功能都走同一套主机`/api`。插件版和网页工作台只是两个前端，不需要改后端语义。

## 3. 目标形态

**插件版：** 安装一次之后，用户只需**打开VS Code → 打开项目文件夹 → 点侧栏“Web Agent”里的【启动】**，全程不需要CMD，也不需要浏览器。

- 主机以当前VS Code工作区为`WORKSPACE_ROOT`、在后台启动。日志进入VS Code“输出”面板的“Web Agent Host”。
- 状态栏显示：未启动 / 准备依赖 / 运行中 / 错误。点状态栏同样可以启动或停止。
- 侧栏顶部是一张“启动”卡片：【启动】【停止】，以及可选的“启动后同时开启Bridge”。Bridge下面直接显示隧道选择、MCP地址、【复制提示词】【重置MCP地址】，把启动和权限放在同一处。
- 模型、Bridge高级、审批、诊断等设置在一个VS Code编辑器标签页“Web Agent 设置”里打开，从侧栏齿轮进入。
- 关闭VS Code窗口时，由插件启动的主机和它拉起的隧道一起停止。

**网页工作台版：** 保持不变，`run-webagent.cmd`照旧启动主机并提供3000端口的工作台。

**两者并存：**

- 如果用户已用`run-webagent.cmd`为同一个工作区启动了主机，插件点【启动】时会核对身份和工作区，然后**直接接管连接**，不重复启动。此时VS Code和网页工作台看到的是同一个主机、同一份设置和任务。
- 插件停止时只停自己启动的主机，不去结束别人启动的主机。

**保持不变的安全边界：**

- Bridge（公网隧道）**永远不自动开启**，必须用户点击。
- 主机默认只听127.0.0.1，`/api`不对外。
- 模式与权限语义不变。
- 危险命令确认、远程拒绝等全部沿用现有实现。

## 4. 设计要点

### 4.1 插件如何找到主机代码（决定D1）

装到`~/.vscode/extensions/`里的插件目录只有插件文件，没有agent-host。推荐做法：`install-desktop-extension.js`安装时在插件目录写入`host.json`，内容包括：

- 主机根目录：源码仓库根，或安装版的runtime目录；
- 来源提交号；
- 插件内容hash。

插件启动时读取这个文件，并在“输出”里打印提交号。这也顺带修复R8偏差c（装旧了看不出来）：侧栏和状态栏悬停可以显示“插件=提交X，主机=提交Y”，两者不一致时提示重装。

另一种做法是把主机和依赖整体打包进插件（VSIX），不再依赖仓库位置。它更独立，但要解决包体积、原生依赖和发布流程，工作量明显更大。建议放到以后再考虑，第一期不做。

### 4.2 启动与进程管理（第一期核心）

- 新增启动模式`launch.js host <工作区>`：等于classic模式加上`WEBAGENT_SKIP_WORKBENCH=1`，复用现有的runtime准备、依赖安装、工作区校验和中止逻辑。插件只负责拉起这一个入口，不另写一套安装逻辑。classic模式不受影响。
- Node来源：
  - 默认用系统`node`，可用新设置`webagent.nodePath`覆盖。
  - 找不到时，侧栏给出明确说明，并提供“运行环境自检”入口。
  - 不改用VS Code内置的Electron来运行，因为那里没有npm，版本也不受控。
- **端口：** 由插件启动的主机从48271开始找一个空闲端口，通过`AGENT_HOST_PORT`传给主机。插件在内存里使用这个地址，不写进用户设置，因此两个VS Code窗口、两个项目可以同时运行。手工设置`webagent.agentHostUrl`时进入“连接已有主机”模式，行为与今天相同。
- **已有主机时接管而非重复启动：** 先读`/api/status`核对身份和工作区。一致就直接连接（例如网页工作台版已启动的主机）；不一致就提示用户，不去抢占端口。
- **停止与清理：**
  - 插件停用时，只停止**自己启动**的主机进程树。Windows上需要确认子进程确实被结束，这一点此前记录为“未验证”，第一期要补测试。
  - 新增一项保险：由插件启动的主机会收到`WEBAGENT_PARENT_PID`，主机定期检查父进程，VS Code崩溃时自己退出，并先停隧道，避免留下占着端口的孤儿进程和cloudflared残留。classic模式不传这个变量，行为不变。现有的“隧道残留回收”作为兜底继续保留。
- **工作区信任：** 在受限模式（未信任的工作区）下不允许启动主机。插件的`package.json`没有声明`capabilities`，按VS Code规则，插件在受限模式下本来就不启用。
- **自动启动（决定D2）：** 默认只在点击时启动。可选设置`webagent.autoStartHost`为true时，打开信任的工作区即自动启动主机，但不启动Bridge。

### 4.3 设置页（第二期）

在VS Code编辑器标签页（WebviewPanel）中实现。所有请求都经扩展进程转发到本机主机：webview不直接访问`127.0.0.1`，也不放宽主机的Origin检查。

**避免两套界面各写一份：** 网页工作台的请求集中在少数几个模块（`settings.js`、`bridge.js`、`operations.js`等）。做法是把其中的`fetch('/api/…')`收拢成一个可替换的请求函数：

- 在网页工作台里，它仍然是`fetch`，行为不变；
- 在插件设置页里，它改成经`postMessage`转发。

这样两个前端共用同一份界面代码，以后改一处两边都生效。要付出的代价是：网页工作台这几个模块需要做一次不改行为的重构，并由现有的浏览器回归测试把关。迁移顺序是：

1. 模型与API Provider；
2. Bridge高级与重置MCP地址；
3. 待批与已执行请求；
4. 诊断；
5. 检查点；
6. 环境偏好、指令、技能等。

## 6. 风险

- **Windows进程树与孤儿进程**：已有记录的未验证点。缓解办法是父进程看护加CI实测，残留回收入口继续兜底。
- **首次启动要联网安装依赖**（`npm ci`，现有两分钟期限）：侧栏显示进度，可以取消，失败时给出原因，不静默重试。
- **两个窗口打开同一个工作区**：第二个窗口按“接管已有主机”处理，不重复启动。
- **两个前端长期并存的维护成本**：通过4.3的共用界面代码控制。第二期里网页工作台的重构只改请求方式，不改界面和行为。
- **插件接管了网页版启动的主机**：此时插件停止不会结束该主机，状态栏会注明“外部启动”，避免用户以为已经关闭。

## 8. 第一期实施记录（2026-09-25）

用户对D1–D4回复“都按推荐”。已实施：

- `launch.js host <工作区>`（`WEBAGENT_SKIP_WORKBENCH=1`，不开3000）；安装脚本写`host.json`（仓库根、来源提交、内容hash）。
- 插件新增`hostManager.js`：先接管同一文件夹的已有主机，否则从48271起找空闲端口后台启动；输出面板“Web Agent Host”；侧栏“主机”卡片（启动/停止/日志、“启动主机后同时开启Bridge”）与隧道下拉框；命令“启动主机/停止主机/查看主机日志”；设置`webagent.nodePath`（machine范围）与`webagent.autoStartHost`（默认关）。
- 主机端`utils/lifeline.js`。

与方案不同或新增之处：

1. **新增stdin生命线**：插件持有主机stdin管道，VS Code以任何方式退出时操作系统关闭管道，主机立即执行自己的shutdown（先停命令与隧道）。父进程PID轮询（5秒）保留为第二道保险。插件点【停止】也走这条路，10秒不退出才强制结束进程树。
2. **状态栏点击只启动不停止**：未启动时点击启动，启动中点击看日志，运行中仍打开侧栏；停止放在侧栏与命令里，避免误点断开远程连接。
3. **未做“运行环境自检”入口**：找不到Node、缺`host.json`、端口占满等都在侧栏卡片和输出面板直接说明原因与处理办法。
4. **端口说明**：48271被别的文件夹的主机或其他程序占用时，插件不接管也不关闭它，改用下一个端口并在卡片上提示，含token模式Named Tunnel入口写死48271时的影响。
5. **生命线变量不外传**：主机启动时读出`WEBAGENT_LIFELINE`/`WEBAGENT_PARENT_PID`后立即从环境删除，Agent执行的命令与命令里再起的主机不会继承（第二轮复审发现的泄漏）。
6. **手工地址判定**：`webagent.agentHostUrl`在package.json有默认值，用`inspect`区分“真的填了”。填了就只连接、不一键启动。

验证：`hostLaunch.test.js`在Linux与Windows CI上真实启动仓库主机，覆盖接管、正常停止（未强杀）、父进程退出、各失败路径；去掉主机端生命线接线时“未强杀”断言失败。**仍需用户实机确认**：Windows桌面关闭VS Code后48271与cloudflared是否释放；先开`run-webagent.cmd`再点【启动】是否接管。安装版（LocalAppData runtime）的`host.json`与一键启动未验证。第二期（设置页）未开始。

**实机验收（2026-09-25，用户Windows桌面，提交`506cd0a`）：通过。** 记录原文归档为[R6第一期实机验收记录](../../review/R6第一期实机验收记录-2026-09-25.md)。上段两项“仍需用户实机确认”均已确认：关闭VS Code后48271、cloudflared与主机进程全部释放（Arena侧随即报隧道不可达）；先开`run-webagent.cmd`再点【启动】只接管、不起第二个主机，插件命令拒绝关闭外部主机，关闭VS Code后CMD里的主机继续运行。自动启动、启动后同时开Bridge、重载窗口、坏nodePath提示均通过。4.7（Chat）因未配置模型记未执行；安装版仍未验证。
