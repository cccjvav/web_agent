## 1. 用户诉求（R8记录末节）

1. 插件启动流程步骤太多。
2. Bridge启动埋在“智能体自定义设置→Bridge页”，和侧栏权限卡片割裂。
3. 期望：装好插件后一切集成、一次运行全部启动。例如插件侧栏提供一个启动按钮，点一下就启动主机和相关服务。
4. 网页工作台和run-webagent唤起的独立网页不再需要，可以去掉。

## 2. 现状事实（按源码核对）

**今天的启动链。** 用户先在CMD运行`run-webagent.cmd`，再由`installer/launch.js classic`启动`agent-host/src/index.js`。主机开两个端口：3000给网页工作台（`WORKBENCH_PORT`），48271给`/api`、`/mcp`和`/ws`（`AGENT_HOST_PORT`）。插件自己**不启动主机**，只按设置`webagent.agentHostUrl`（默认48271）去连接；主机的工作区和VS Code打开的文件夹不一致时，状态栏显示“工作区不一致”。

**插件已有的能力**（`webagent-core/extension/extension.js`，约800行）：

- 活动栏“Web Agent”下有两个视图。
  - **Chat & Agent**：流式调用`/api/chat`。
  - **Bridge 模式 (远程指挥台)**：显示MCP地址，有**启动 Bridge / 停止 / 复制提示词 / 重置密钥**按钮，另有工作模式切换、四项权限、任务与日志。
- Chat参与者`@webagent`、PTY终端执行、草稿差异预览，以及状态栏。

**更正R8中的一处观察。** R8第5步和第5条反馈所说的“侧栏只有模式与权限”，指的是**网页工作台**的侧栏卡片。VS Code插件的“Bridge 模式”视图其实已经有启动按钮，只是隧道写死为Cloudflare Quick Tunnel（`tunnelProvider:'cloudflare'`），而且主机必须已经由CMD启动。它也可能被折叠在Chat视图下方而不显眼。所以割裂的真正原因是：**主机只能在插件外启动；Bridge高级选项、模型设置和审批入口只在网页工作台里**。

**只有网页工作台才有的功能**（`webagent-core/workbench`，约4300行）：

| 功能 | 主机接口 | 去掉网页后的去向 |
|---|---|---|
| 文件树与Monaco编辑器 | `/api/files/*` | VS Code本身就有，直接去掉 |
| 网页Chat | `/api/chat` | 插件Chat视图已有，直接去掉 |
| **模型与API Provider**（新增/探测/切换） | `POST /api/models`、`/api/providers/probe` | **必须迁移**：没有它，插件Chat无模型可用（R8的9.2正是因此未执行） |
| Bridge高级：隧道选择（Quick/Named/ngrok）、域名/Token、客户端提示、重置MCP地址、OAuth设备配对 | `/api/bridge/*` | 迁移 |
| **待批与已执行请求**（外部请求、固定工作流的本机批准） | `/api/operations/*`、`/api/workflows/*` | **必须迁移**：这是本机审批的唯一入口，不能随网页一起消失 |
| 主机身份与能力诊断、连接核对 | `/api/diagnostics`、`/api/connection-checks` | 迁移（排障要用） |
| 跨文件检查点恢复 | `/api/checkpoints/*` | 迁移 |
| stdio MCP / 外部MCP服务器 | `/api/external/*` | 待决定（第7节D6） |
| 环境偏好、技术栈、智能体、指令、提示、技能 | `/api/customizations`、`/api/skills`、`/api/profile/detect` | 迁移（这些写入工作区的`.webagent`，也可以直接编辑文件） |
| 多模型博弈 | `/api/consensus/run` | 待决定（D6） |
| 探针链接 | `/api/probe/*` | 探针暂停中，另一助手负责，本方案不动 |

**可以直接复用的基础：**

- 主机已支持`WEBAGENT_SKIP_WORKBENCH=1`，即不开3000端口的纯主机模式（原本给code-server用）。
- `launch.js`已有依赖准备，带期限和取消（`ensureDependencies`/`preparation.js`），还有工作区解析。
- 插件已有“扩展进程代理请求、webview不直接访问主机”的模式（`requestJson`加`postMessage`）。主机的`/api`只接受本机回环，并拒绝跨站Origin，这个安全边界保持不变。

## 3. 目标形态

安装一次之后，用户只需：**打开VS Code → 打开项目文件夹 → 点侧栏“Web Agent”里的【启动】**。

- 主机以当前VS Code工作区为`WORKSPACE_ROOT`、在后台启动，不打开任何网页或CMD窗口。日志进入VS Code“输出”面板的“Web Agent Host”。
- 状态栏显示：未启动 / 准备依赖 / 运行中 / 错误。点状态栏同样可以启动或停止。
- 侧栏顶部是一张“启动”卡片：【启动】【停止】，以及可选的“启动后同时开启Bridge”。Bridge下面直接显示隧道选择、MCP地址、【复制提示词】【重置MCP地址】，把启动和权限放在同一处。
- 模型、Bridge高级、审批、诊断等设置在一个VS Code编辑器标签页“Web Agent 设置”里打开，从侧栏齿轮进入，替代网页工作台的设置弹窗。
- 关闭VS Code窗口时，主机和它拉起的隧道一起停止。

**保持不变的安全边界：**

- Bridge（公网隧道）**永远不自动开启**，必须用户点击。
- 主机默认只听127.0.0.1，`/api`不对外。
- 模式与权限语义不变。
- 危险命令确认、远程拒绝等全部沿用现有实现。

## 4. 设计要点

### 4.1 插件如何找到主机代码（决定D1）

装到`~/.vscode/extensions/`里的插件目录只有插件文件，没有agent-host。推荐做法：`install-desktop-extension.js`安装时在插件目录写入`host.json`，内容包括：

- 主机根目录：源码仓库根，或安装版的runtime目录；
- 来源提交号；
- 插件内容hash。

插件启动时读取这个文件，并在“输出”里打印提交号。这也顺带修复R8偏差c（装旧了看不出来）：侧栏和状态栏悬停可以显示“插件=提交X，主机=提交Y”，两者不一致时提示重装。

另一种做法是把主机和依赖整体打包进插件（VSIX），不再依赖仓库位置。它更独立，但要解决包体积、原生依赖和发布流程，工作量明显更大。建议放到以后再考虑，第一期不做。

### 4.2 启动与进程管理（第一期核心）

- 新增启动模式`launch.js host <工作区>`：等于classic模式加上`WEBAGENT_SKIP_WORKBENCH=1`，复用现有的runtime准备、依赖安装、工作区校验和中止逻辑。插件只负责拉起这一个入口，不另写一套安装逻辑。
- Node来源：
  - 默认用系统`node`，可用新设置`webagent.nodePath`覆盖。
  - 找不到时，侧栏给出明确说明，并提供“运行环境自检”入口。
  - 不改用VS Code内置的Electron来运行，因为那里没有npm，版本也不受控。
- **端口：** 由插件管理的主机从48271开始找一个空闲端口，通过`AGENT_HOST_PORT`传给主机。插件在内存里使用这个地址，不写进用户设置，因此两个VS Code窗口、两个项目可以同时运行。手工设置`webagent.agentHostUrl`时进入“连接已有主机”模式，行为与今天相同。
- **已有主机时接管而非重复启动：** 先读`/api/status`核对身份和工作区。一致就直接连接；不一致就提示用户，不去抢占端口。
- **停止与清理：**
  - 插件停用时停止主机进程树。Windows上需要确认子进程确实被结束，这一点此前记录为“未验证”，第一期要补测试。
  - 新增一项保险：主机收到`WEBAGENT_PARENT_PID`后定期检查父进程，VS Code崩溃时自己退出，并先停隧道，避免留下占着端口的孤儿进程和cloudflared残留。现有的“隧道残留回收”作为兜底继续保留。
- **工作区信任：** 在受限模式（未信任的工作区）下不允许启动主机。按VS Code规则，插件在受限模式下本来就不启用。
- **自动启动（决定D2）：** 默认只在点击时启动。可选设置`webagent.autoStartHost`为true时，打开信任的工作区即自动启动主机，但不启动Bridge。

### 4.3 设置页（第二期）

在VS Code编辑器标签页（WebviewPanel）中实现。所有请求都经扩展进程转发到本机主机：webview不直接访问`127.0.0.1`，也不放宽主机的Origin检查。复用方式：网页工作台的请求集中在少数几个模块（`settings.js`、`bridge.js`、`operations.js`等），可以把其中的`fetch('/api/…')`换成一个经`postMessage`转发的适配函数，界面代码尽量原样搬过去，避免两套实现长期分叉。迁移顺序是：

1. 模型与API Provider；
2. Bridge高级与重置MCP地址；
3. 待批与已执行请求；
4. 诊断；
5. 检查点；
6. 环境偏好、指令、技能等。

### 4.4 去掉网页工作台（第三期，决定D3–D5）

前提：第二期确认迁移的功能在插件中全部可用，并通过用户实机验收。之后再做：

- 主机不再提供3000端口和`workbench/`静态页面；
- 删除`run-webagent.cmd`唤起网页的行为；
- 相应清理安装器入口；
- 重写`使用指南.md`、启动脚本说明和各验收手册。

历史保留文档不改。需要删除的代码会先列出清单，并给出对应测试的去留。

## 6. 风险

- **Windows进程树与孤儿进程**：已有记录的未验证点。缓解办法是父进程看护加CI实测，残留回收入口继续兜底。
- **首次启动要联网安装依赖**（`npm ci`，现有两分钟期限）：侧栏显示进度，可以取消，失败时给出原因，不静默重试。
- **两个窗口打开同一个工作区**：第二个窗口按“接管已有主机”处理，不重复启动。
- **第三期文档改动面很大**：大量文档引用网页工作台。第三期会单独盘点需要修改的文档清单再动手。
- **code-server（网页VS Code）模式**：插件自启主机后，code-server模式在原理上也能用同一套逻辑。是否保留见D4。
