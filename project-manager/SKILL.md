# 项目管家 v12

## 核心理念

三层渐进式信息架构，让任何 AI Agent 在最短上下文内了解项目全貌，再按需深入：

| 层级 | 文件 | 何时读 | 回答什么问题 |
|------|------|--------|-------------|
| **L0 入口** | `AGENTS.md`（项目根目录） | Agent 启动时 | 这个项目有什么规则？去哪读？ |
| **L1 概览** | `manager/CONTEXT.md` + `manager/agents.md` | 紧跟 L0 | 项目是什么？做到哪了？有什么约定？ |
| **L2 详情** | `manager/stages/` + `manager/docs/` | 按任务需要 | 具体怎么做？踩过什么坑？ |

**核心原则：启动只读 L0+L1（< 100 行），L2 按需加载，禁止预加载全部文档。**

## 跨工具适配

项目管理的规则存在两处：
- **Skill 源文件**（本文件）：支持 Skill 的工具（Trae/Qoder 等）直接触发
- **manager/SKILL.md**（规则副本）：初始化时从 Skill 源文件复制到项目内，供不支持 Skill 的工具（Aider/Claude Code 等）离线读取

不支持 Skill 的工具通过项目根目录 `AGENTS.md` 发现入口，按指引读取 `manager/SKILL.md` 获取完整规则，再进入正常工作流。

| 工具类型 | 代表 | Skill 支持 | 规则获取方式 |
|----------|------|-----------|-------------|
| IDE 类 | Trae、Qoder | ✅ | Skill 自动触发 |
| CLI 类 | Aider、Claude Code | ❌ | AGENTS.md → manager/SKILL.md |

> `manager/SKILL.md` 是只读副本，禁止在项目内修改；Skill 升级时手动同步。项目特色规则写入 `manager/agents.md`。

## 项目运行时目录结构

```
<项目根目录>/
├── AGENTS.md                ← L0 入口：所有 AI Agent 启动时读取，路由到 manager/
└── manager/
    ├── SKILL.md             ← 规则副本（不支持 Skill 的工具必读，支持的可选读）
    ├── CONTEXT.md           ← L1 项目索引（< 80 行）：项目身份、当前状态、导航规则
    ├── agents.md            ← L1 项目约定：技术环境、编码规范、开发流程等无需索引的通用约定
    ├── privacy.md           ← 隐私映射：占位符 {{xxxx}} → 真实数据（敏感文件，按需读取，严禁外泄）
    ├── stages/              ← L2 阶段记录：按开发阶段记录需求、设计、决策、复盘
    │   ├── s1-<名称>.md
    │   └── s2-<名称>.md
    ├── docs/                ← L2 专项文档：架构、API、规范、经验等深度文档
    │   ├── architecture.md
    │   ├── api.md
    │   ├── conventions.md
    │   ├── troubleshooting.md
    │   └── experience.md
    └── user-manual/         ← 使用手册：面向所有角色（非仅开发者）的操作指南
        ├── README.md
        ├── architecture.md
        ├── setup.md
        ├── development.md
        ├── debugging.md
        └── ui-guide.md
```

> **AGENTS.md（根目录，大写）** vs **manager/agents.md（小写）**：完全不同的文件。
> - `AGENTS.md`：跨工具通用入口，所有 AI Agent 自动读取，负责路由引导
> - `manager/agents.md`：项目约定，记录技术环境、编码规范等"不需要索引就能找到的项目约定"

# 快速上手

## 第 1 步：初始化

用户说"初始化项目管理"或"创建项目管家"时：

```bash
mkdir -p manager/stages manager/docs manager/user-manual
# 将本 SKILL.md 复制为项目内规则副本
cp <skill包路径>/SKILL.md manager/SKILL.md
```

创建最小化 `manager/CONTEXT.md`（模板见下方「文件规范」）。

## 第 2 步：创建 AGENTS.md（项目根目录）

在项目根目录创建或更新 `AGENTS.md`：

- **已存在**：检查是否已包含「项目管理」模块。有则不改；没有则在末尾追加，不动已有内容。
- **不存在**：创建新文件，写入以下内容：

```markdown
<!-- 以下内容由 project-manager 自动生成与维护 -->

## 项目管理

本项目使用 project-manager 规则进行推理型项目管理。任何 AI Agent 处理本项目任务时，须遵循以下规则。

### 启动顺序
1. 读取 `manager/CONTEXT.md`（项目索引，< 80 行）
2. 读取 `manager/agents.md`（项目约定）
3. 不支持 Skill 的工具（Aider/Claude Code 等）：在步骤 1 之前先读 `manager/SKILL.md` 获取完整规则
4. 按 CONTEXT.md 的「导航规则」按需读取其他文件，禁止预加载全部

### 触发项目管理的时机
- 开始新上下文或接手项目
- 需要了解项目当前状态
- 进入新开发阶段（新功能模块、架构变更、版本迭代等里程碑）
- 完成开发后更新项目记录
- 用户要求生成使用手册
- 用户提到"项目管家""更新项目记录""生成手册"
- 需要写入用户隐私/敏感信息（API Key、姓名、身份证号等）

### 完成开发后必做
1. 更新 `manager/CONTEXT.md` 的「当前状态」（通常只改 2-3 行）
2. 在 `manager/stages/` 当前阶段文件追加关键决策和经验
3. 有复用价值的经验同步到 `manager/docs/experience.md`
4. 检查 CONTEXT.md 非阶段摘要区域是否超 80 行

### manager/ 目录
```
manager/
├── SKILL.md          ← 规则全文（不支持 Skill 的工具必读）
├── CONTEXT.md        ← 项目索引（启动必读，< 80 行）
├── agents.md         ← 项目约定（技术环境、编码规范）
├── privacy.md        ← 隐私映射（{{占位符}} → 真实数据，按需读取）
├── stages/           ← 阶段记录（按需读取）
├── docs/             ← 专项文档（按需读取）
└── user-manual/      ← 使用手册（面向所有角色）
```

### 注意事项
- manager/ 下所有文件首行必须有定位说明 `<!-- 定位：... -->`
- CONTEXT.md 只放"是什么"和"在哪"，不放"怎么做"
- experience.md 只沉淀可复用经验，偶发问题不记录
- manager/SKILL.md 是只读副本，禁止修改
- 涉敏信息（API Key、姓名、身份证号、地址、身份、IP 等）一律用 {{占位符}} 写入管理文件，真实数据只存 manager/privacy.md
```

## 第 3 步：开始开发阶段

用户说"开始新阶段"或"进入阶段N"时：
1. 在 `manager/stages/` 创建阶段文件 `sN-<名称>.md`
2. 更新 CONTEXT.md 的「当前状态」
3. 开始记录开发过程

## 第 4 步：生成使用手册（可选）

用户说"生成使用手册"时：
1. 扫描项目结构（目录树、pom.xml / package.json / requirements.txt 等）
2. 读取 manager/docs/ 已有文档
3. 分析核心代码文件
4. 生成 `manager/user-manual/` 下手册文件

# 自动阶段检测

**触发条件（同时满足）：**
1. 新对话开始
2. CONTEXT.md 中「正在做」与本次任务方向显著不同（新模块、新需求、架构变更等）
3. 当前阶段文件未记录本次任务

**执行：**
1. 创建新阶段文件 `s<N>-<名称>.md`
2. 更新 CONTEXT.md「当前状态」
3. 告知用户："检测到可能进入新阶段，已创建 s<N>-<名称>.md，是否正确？"
4. 用户确认后继续；否认则合并到当前阶段

> 小修小补（修 bug、调样式、改配置）不算新阶段。新阶段 = 新的可交付里程碑。不确定就先问。

# Agent 工作流

## 新上下文启动
1. 不支持 Skill 的工具：先读 `manager/SKILL.md` 获取规则全文
2. 读 `manager/CONTEXT.md`（< 80 行）
3. 读 `manager/agents.md`（项目约定）
4. 若根目录存在 `AGENTS.md`，读取其中的「项目管理」模块
5. **不读其他文件**——除非当前任务明确需要

## 接到具体任务
1. 对照 CONTEXT.md「导航规则」判断需要读哪个 L2 文件
2. 对照 agents.md 的项目约定调整行为
3. **只读相关文件**

## 完成开发后
1. 在 stages/ 当前阶段文件追加开发点和决策
2. 更新 CONTEXT.md 的「当前状态」（通常 2-3 行）
3. 有长期价值的知识写入 docs/
4. 有复用价值的经验同步到 docs/experience.md
5. 若发现新的项目约定，更新 agents.md
6. 检查 stages/「待更新文档」清单并处理
7. **执行自检清单**

### 自检清单
- [ ] CONTEXT.md「当前状态」反映最新进度？
- [ ] stages/ 当前阶段文件记录了关键决策和经验？
- [ ] 导航规则指向的文件都存在？
- [ ] 新增经验已同步到 experience.md（如有复用价值）？
- [ ] experience.md 无重复条目？
- [ ] CONTEXT.md 非阶段摘要区域 ≤ 80 行？
- [ ] 涉敏数据均用 {{占位符}} 且已在 privacy.md 登记？

## agents.md 模板（项目约定）

agents.md 记录项目级的通用约定——不需要索引就能找到的、对项目所有任务都适用的规则。不是 Agent 人设，是项目约定。

```markdown
<!-- 定位：项目约定，记录技术环境、编码规范、开发流程等对所有任务通用的项目级约定 -->

# [项目名] 项目约定

## 技术环境
- **语言/版本**：如 Java 17 / Python 3.12
- **构建工具**：如 Maven 3.9 / Gradle 8.x
- **框架版本**：如 Spring Boot 3.2 / Vue 3.4
- **数据库**：如 MySQL 8.0 / PostgreSQL 16
- **运行环境**：如 JDK 17 / Node 20

## 编码规范
- **命名**：如 类名 PascalCase，方法名 camelCase，常量 UPPER_SNAKE
- **结构**：如 单函数不超过 50 行，超过必须拆分
- **异常处理**：如 统一异常处理器 + 自定义业务异常体系
- **注释**：如 公共方法必须写 JavaDoc，复杂逻辑必须写行注释

## 开发流程
- **分支策略**：如 main 为保护分支，开发用 feature/* 分支
- **提交规范**：如 feat: / fix: / docs: / refactor: 前缀
- **代码审查**：如 PR 必须至少一人 review 后合并

## 工具偏好
- **优先使用**：如 优先用 MyBatis-Plus 而非手写 SQL
- **避免使用**：如 禁止用 Lombok @Data（团队约定）

## 领域知识
- **业务术语**：如"司库"指企业资金集中管理系统
- **核心概念**：如 本项目的"融资方"指租赁业务中的承租人
```

# 隐私信息处理

**铁律：manager/ 任何文件禁止写入用户隐私/敏感信息的真实值，一律使用占位符 `{{xxxx}}`。真实数据只存在于 manager/privacy.md。**

## 占位符规则
- **格式**：`{{含义}}`，含义用简短中文或英文描述，如 `{{api_key}}`、`{{真实姓名}}`、`{{身份证号}}`、`{{IP地址}}`
- **适用范围**：API Key、Token、密码、姓名、身份证号、手机号、地址、身份信息、IP、内网路径等一切隐私/敏感信息
- **一致性**：同一真实数据在多处出现时使用相同的占位符；同一占位符可被多个文件引用

## privacy.md 记录格式
每条记录一行：

```
原文件<文件名> {{占位符}} ：真实数据
```

示例：

```
原文件<manager/agents.md> {{api_key}} ：sk-xxxxxxxxxxxx
原文件<manager/stages/s2-xxx.md> {{真实姓名}} ：张三
原文件<manager/docs/experience.md> {{手机号}} ：138xxxxxxxx
```

## 操作流程
1. **写入前**：需要写入敏感信息 → 先创建占位符 `{{xxxx}}`，再在 privacy.md 登记
2. **读取时**：遇到 `{{xxxx}}` → 查 privacy.md 获取真实含义（仅当前任务需要时）
3. **修改后**：占位符或对应内容变化 → 同步更新 privacy.md，保持一一对应

## 安全边界
- privacy.md 是敏感文件：按需读取，不参与启动加载；禁止写入使用手册、评审文档或任何对外输出
- 生成 user-manual、docs/ 时，涉及占位符的内容只保留占位符本身，不展开真实数据
- 使用 git 的项目建议将 privacy.md 加入 .gitignore 或放入私有仓库

# 项目健康度检查

**触发时机**：新对话/接手项目、用户问"项目什么情况"、自检发现问题。

| 检查维度 | 检查项 |
|----------|--------|
| **CONTEXT.md** | 非阶段摘要区域 ≤ 80 行？「当前状态」与实际一致？导航规则指向的文件存在？阻塞项是否仍准确？ |
| **阶段文件** | 有无孤儿阶段（文件存在但 CONTEXT.md 未引用）？是否记录了"为什么"而非仅"做了什么"？「待更新文档」积压是否超 10 项？ |
| **经验文档** | 有无重复条目？有无"假经验"（偶发问题无复用原则）？标签体系是否一致？ |
| **隐私文件** | privacy.md 占位符与实际使用一致？有无敏感数据直接写入其他文件？ |
| **文档一致性** | CONTEXT.md 标记"进行中"的阶段在 stages/ 有对应文件？已完成阶段在 CONTEXT.md 摘要中有记录？experience.md 引用的阶段文件存在？ |

检查后输出报告：
```
📋 项目健康度检查
- CONTEXT.md：✅ / ⚠️ [问题描述]
- 阶段文件：✅ / ⚠️ [问题描述]
- 经验文档：✅ / ⚠️ [问题描述]
- 隐私文件：✅ / ⚠️ [问题描述]
- 文档一致性：✅ / ⚠️ [问题描述]
- 建议操作：[修复事项列表]
```

# 常见错误

| 错误 | 后果 | 正确做法 |
|------|------|----------|
| CONTEXT.md 超 80 行 | 启动变慢，违背按需加载 | 只放"是什么"和"在哪"，详细内容移到 stages/ 或 docs/ |
| 不写定位说明 | 新 Agent 不知道每个文件干什么 | 所有文件首行写 `<!-- 定位：... -->` |
| 阶段文件只记结果 | 丢失决策过程和踩坑经验 | 记录"为什么"比"做了什么"重要 |
| agents.md 写笼统规则 | "代码要规范"等于没说 | 写具体的、可执行的约定（如"单函数不超过 50 行"） |
| 文档写完不更新 | 文档与代码不一致，误导新人 | 每次开发后检查文档，stages/ 记录待更新清单 |
| experience.md 只加不删 | 过时经验误导 Agent | 每条带标签和日期，技术栈变更时清理过时经验 |
| 使用手册只给开发者看 | 产品/运营看不懂 | 按角色分层，非技术角色有专门章节 |
| manager/SKILL.md 被修改 | 规则副本与源文件不一致 | SKILL.md 只读，项目特色规则写 agents.md |
| 敏感信息直接写入管理文件 | 隐私泄露，真实数据可能被 Agent 输出或误入文档 | 一律用 {{占位符}}，真实数据只存 privacy.md |

# 适用范围

| ✅ 适合 | ❌ 不适合 |
|---------|----------|
| 中大型项目（代码量大、模块多） | 一次性脚本/小工具（管理成本 > 收益） |
| 团队协作项目（需统一上下文） | 个人练手项目（简单 README 即可） |
| 长期维护项目（需记录开发历程） | 快速原型/MVP（先跑通再文档化） |
| 知识密集型项目（需沉淀领域知识） | 纯前端静态页面（逻辑简单） |
| 面向非技术用户（需使用手册） | 开源库/SDK（有专门文档工具） |

# 异常处理

| 情况 | 处理 |
|------|------|
| CONTEXT.md 超 80 行 | 把"怎么做"移到 stages/ 或 docs/，用表格和链接代替长段落 |
| 阶段文件冲突（多人开发） | 按模块拆分（如 `s2-frontend.md`、`s2-backend.md`） |
| 项目暂停后重启 | 先更新 CONTEXT.md「当前状态」，再开始新工作 |
| 技术栈频繁变更 | CONTEXT.md 用"当前技术栈"+"历史技术栈"分区 |
| 文档和代码不一致 | 立即修复文档，stages/ 记录原因，建立 PR 文档检查机制 |
| manager/SKILL.md 不存在 | 提示用户运行初始化或手动复制 SKILL.md |
| manager/SKILL.md 版本过旧 | 以 Skill 源文件为准，提示用户同步 |
| Aider/Claude Code 未读取 AGENTS.md | 在项目 README 中提示配置工具读取（如 aider 的 `--read` 参数） |
| 发现敏感数据已写入管理文件 | 立即替换为 {{占位符}}，将真实值登记到 privacy.md |

# 核心原则

1. **按需加载**：启动只读 L0+L1（AGENTS.md + CONTEXT.md + agents.md），L2 按需读取
2. **CONTEXT.md 是导航图**：回答"是什么、做到哪、详情在哪"，不回答"怎么做"
3. **80 行铁律**：CONTEXT.md 非阶段摘要区域 ≤ 80 行
4. **文件首行标注定位**：manager/ 下所有文件首行写明用途
5. **agents.md 是项目约定**：技术环境、编码规范、开发流程，不是 Agent 人设
6. **记录"为什么"比"做了什么"重要**：决策过程和踩坑经历是核心资产
7. **文档和代码同步**：每次开发后检查文档是否需要更新
8. **渐进式建设**：所有文件按需创建，不强制初始化全部
9. **经验只沉淀可复用的**：偶发问题不写 experience.md，技术栈变更时清理过时经验
10. **跨工具兼容**：AGENTS.md 通用入口 + manager/SKILL.md 规则副本，让任何工具都能独立执行规则
11. **规则副本只读**：manager/SKILL.md 禁止修改，项目特色规则写 agents.md，Skill 升级时手动同步
12. **自动阶段检测**：新对话 + 显著变更 = 可能进入新阶段，主动提示
13. **完成必自检**：每次开发后执行自检清单
14. **手册面向所有角色**：非仅开发者，产品/测试/运维都能获取所需信息
15. **隐私占位符化**：涉敏信息一律用 {{占位符}}，真实数据只存 privacy.md，按需读取
