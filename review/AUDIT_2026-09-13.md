## D. 表述歧义（低风险，建议顺手改）

### D1. 「按钮仍成功」应为「请求仍 200 但 success:false」
- `组件说明.md` §3.3：「没有二进制或缺 Token 时按钮仍成功，MCP 走当前页面源」；`使用指南.md` §7 第 5 条：「按钮仍成功（toast 会提示）」；`架构导读.md` §7 / §11 同句。
- 代码事实（`src/api/routes.js` `/bridge/start`）：无二进制/缺 Token/超时 → `tunnelError` 置位 → `success:false, running:false` + `note` 说明；HTTP 仍是 200。
- **修法**：统一为「启动请求仍返回 200，但 `success:false`，toast/`note` 说明原因；MCP 地址停在当前页面源（本机预览可用，云端连不上）」。

### D2. `组件说明.md` §3.1「若没装过依赖就 npm install」与实际命令不符
- 实际：`installer/launch.js` `ensureDependencies` 在 `node_modules/express` 缺失时执行 **`npm ci --omit=dev`**（不是 npm install），且只认 express 标记。
- 后果（值得写清楚）：启动器自动安装**不含** dev 依赖（Acorn），之后跑 `node docs-site/check-docs.js` 会缺依赖，需要开发者自行 `npm ci`。`Windows新手逐步验收.md` 第 4 步处理正确，但 组件说明/使用指南 的「npm install」措辞对不上。
- **修法**：改为「若没装过依赖就 `npm ci --omit=dev`（不含 Acorn 等开发依赖；文档校验前需另跑 `npm ci`）」。

## E. 代码健壮性观察（可选修复，非本次文档范围）

### E1. workbench 启动：WS 事件流被 5 个 fetch 串行卡住，且无重试
- `webagent-core/workbench/app.js` `boot()`：`await Promise.all([refreshStatus, loadTree, loadSkills, loadCustomizations, loadMonaco])` 之后才 `connectWs()`。
- `refreshStatus`（bridge.js L332）、`loadTree`（tabs.js L179）等对 `fetch` **没有 try/catch**：页面加载瞬间任一请求失败（服务器重启中、瞬时 500、代理抖动）→ Promise.all reject → `boot().catch` 只打日志 → **`connectWs()` 永不执行**。
- `scheduleWsReconnect()` 只在**已有 socket 的 onclose** 时触发，这里根本没有 socket，所以「事件流重连中」也不会出现，BRIDGE 卡片静默失活，只有手动刷新页面才恢复。
- `js/启动与Chat详解.md` 已如实描述该行为（「某个未自捕获Promise拒绝会阻止后续WS初始化」）——文档没撒谎，但行为本身值得修：
  - 每个初始化 `await x.catch(() => {})`（失败各自降级），并把 `connectWs()` 移到 `Promise.all` 之外先行/并行启动。
  - 修码后同步更新 启动与Chat详解.md 对应句。

### E2. 版本回退值 '0.6.9' 硬编码两处
- `webagent-core/agent-host/src/extensionVersion.js` 与 `webagent-core/scripts/ensure-code-server.js` 各写死回退 `'0.6.9'`。仅在读 `extension/package.json` 失败时生效，目前无实际风险，但升版时两处要同步改，建议注释互相指向或直接删回退（读不到就直接报错）。

### E3. （与 C3 重叠，记录备查）安装版无 `run-tests.cmd` / `tests/` / `scripts/`
- 有意排除（安装版不跑测试），但 `使用指南.md` 被收进包，其 §12 仍教用户跑 `run-tests.cmd`。按 C3 方案 1 处理时在安装版语境加一句「源码仓库才有测试入口」。

## H. 其他可优化点（问题清单之外的改进建议）

> 分级：[代码] 需要改代码（建议单独评估＋补测试）；[CI] 只动工作流；[DX] 开发体验；[产品方向] 需要你拍板，默认不做。
> 以下均为**建议**，不是已确认缺陷；与 A–F 的区分：A–F 是"文档/行为与事实不符"，H 是"目前能跑，但可以更好"。

### H1 [代码·中优先] 隧道子进程在异常退出时残留（公网门牌继续挂）
- 事实（已核码）：cloudflared / ngrok 都以 `stdio: ['ignore','pipe','pipe']` spawn（脱离控制台）。
  - `src/tunnel/cloudflared.js` 末尾注册了 `process.on('exit'/'SIGINT'/'SIGTERM')` 调 `stopTunnel()`；`stopTunnel()` 内部也会调 `ngrok.stopNgrok()`。所以 **Ctrl+C / 正常停止** 时两者都会被 `taskkill /t /f`（Windows）/ SIGTERM 清掉。
  - `src/tunnel/stopProcess.js` 是**异步**的（1.5s 宽限 + 3s 期限）：`process.on('exit')` 回调里只能执行到第一个 await，POSIX 上 `proc.kill('SIGTERM')` 同步生效，Windows 上 `spawn('taskkill',...)` 通常来得及，但**不保证**。
  - **ngrok.js 自身没有任何 process 级处理器**，完全依赖 cloudflared.js 模块被加载（实际总是被 routes.js 引入，故一般成立）。
  - 因此：node 进程被 `taskkill /F`、窗口强杀、崩溃、断电时，**隧道进程会残留**，公网 URL 继续指向 48271（若你之后重启产品，旧隧道会连上新进程）。
- 建议（按成本排序）：
  1. 最低成本：在 `隧道使用指南.md`「不要做的事」与 `SECURITY.md` 补一句「强杀进程/断电后，请确认 cloudflared/ngrok 已随进程退出（任务管理器），否则公网门牌仍在」；
  2. 中成本：启动隧道时把 pid 写入工作区 `.webagent/tunnel.json`（gitignore），**下次启动产品时**先尝试回收上一轮的孤儿隧道（按 pid + 命令行特征）；
  3. 高成本（Windows）：用 Job Object（`CreateJobObject` + `AssignProcessToJobObject` + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`）把隧道挂进 job，node 进程句柄关闭即整组回收——需要 native 模块，与"无 native 依赖"取向冲突，默认不做。
- 补测试：stub `process.emit('SIGINT')` / `process.exit` 路径，断言 stop 链被触发（现有 tunnel/bridgeTunnel 测试只覆盖显式 stop）。

### H2 [代码·小修] run-webagent.sh 相对工作区路径必然失败
- 事实（已核码）：`run-webagent.sh` 对 `$1` 的 `[ -d ]` 检查发生在**调用者 cwd**；随后 `cd webagent-core/agent-host`，而 `config.js` 用 `path.resolve(process.env.WORKSPACE_ROOT)` 解析——相对路径会落到 **agent-host 目录**下。于是「检查通过但启动必报 WORKSPACE_ROOT 不存在」。
- `启动脚本说明.md` 已如实披露（"经典脚本会在检查工作区后切换 cwd…建议传已存在的绝对目录"），不是文档撒谎，但一行可修：
  ```bash
  case "$1" in /*) ;; *) export WORKSPACE_ROOT="$(pwd)/${1}" ;; esac
  ```
  （放在 `export WORKSPACE_ROOT="$1"` 之前；`run-webagent-vscode.sh` 同理。）修后同步更新 启动脚本说明.md 该段表述。Windows 侧 `launch.js` 本来就按调用者 cwd 解析，无需改。

### H3 [代码/测试·小] 版本 0.6.9 散落 6 处，缺一处一致性守卫
- 事实：单一事实源是 `webagent-core/extension/package.json`（0.6.9），但还有：
  1. `installer/webagent.iss` `#define AppVer "0.6.9"`（默认值）
  2. `agent-host/src/extensionVersion.js` 回退 `'0.6.9'`
  3. `scripts/ensure-code-server.js` 回退 `'0.6.9'`
  4. `extensions-installed/webagent.webagent-core-0.6.9/` 目录名
  5. `tests/extensionCopy.test.js` 硬编码同一目录名
  6. `manager/CONTEXT.md` 等文档里的版本表述
- 现状：升版漏改时 extensionCopy 测试会**失败**（好事），但 .iss 默认值与两个代码回退会**静默**变旧。
- 建议：`installerPackaging.test.js` 加一条断言：.iss 中 `#define AppVer` 的值 == extension/package.json 的 version；两个 `'0.6.9'` 回退改为读不到时直接抛错（或注释互相指向）。升版流程写进 `CONTRIBUTING.md`（一条命令：改 package.json → 同步目录名/测试 → npm test）。

### H4 [CI·小] 依赖审计与 Node 版本矩阵
- 现状：所有 `npm ci/install` 都带 `--no-audit --no-fund`；CI 只跑 Node 20（Linux）/22（Windows），而 `engines` 写 `>=18`。
- 建议：
  1. Linux job 末尾加 `npm audit --omit=dev --prefix webagent-core/agent-host`（先**非阻断**，观察一轮再决定阻断）；
  2. Linux job 的 `node-version` 改为矩阵 `[18, 20, 22]`，或把 `engines` 提到 `>=20` 与 CI 对齐（二选一，保持一致即可）。

### H5 [DX·小] docs-site 服务每次启动都全量重建
- 事实：`serve.js` 启动即 `spawnSync(build.js)`（读 166 个源文件、重写 2MB content.js，约 0.3s）。当前规模无感，但两个改进点：
  1. 加 `DOCS_NO_BUILD=1`（或 `--no-build`）跳过重建，便于改文档正文时快速刷新；
  2. `content.js` 单文件 2MB 且**含全部源码快照**，每次改源码都会产生 2MB 的 Git diff 噪音。若未来嫌噪，可拆成 `content.js`（正文，提交）+ 按文件的 `sources/<hash>.js`（快照，gitignore，serve 时按需加载）；当前保留现状也可以，属取舍不是缺陷。

### H6 [DX·小] 安装版/开发版测试入口差异
- `run-tests.cmd` 带 `pause`（交互入口，CI 不能用——文档已声明）；安装版 payload 又不含 `run-tests.cmd`/`tests/`（有意）。可选改进：`run-tests.cmd` 支持 `WEBAGENT_NO_PAUSE=1` 跳过 pause，方便脚本化；并在安装版携带的 `使用指南.md` §12 加半句「测试入口只在源码仓库」。（与 C3/E3 联动处理）

### H7 [产品方向·需拍板] 「黑窗口必须常开」的稳健性
- 全产品文档都以「黑色 CMD 窗口一直开着」为前提。这是刻意的透明设计（非 Electron、非服务），但意味着：关窗=服务停（+ H1 隧道残留风险）、崩溃无自愈。
- 可选方向（**默认不做**，若做必须保持"用户知情、可关"）：安装器加一个可选任务「后台运行（任务计划程序）」：开机/手动触发 `launch.js classic`，日志写 `LocalAppData/WebAgent/logs/`，工作台仍打 3000，隧道仍走同一 stop API，卸载时清任务。不引入隐藏自启。

### H8 [产品方向·需拍板] 多工作区/多实例
- 现状：一个 agent-host 实例 = 一个工作区（board、read-hashes、plan 轮次、命令表都是全局单例——架构导读 §12 明确"不按客户端隔离全部全局状态"）。同时改两个仓库只能停掉重启，或起第二实例。
- 可选方向（默认不做，改动面大）：
  1. 低成本：官方"双实例"用法文档化（`set AGENT_HOST_PORT=48272 & set WORKBENCH_PORT=3001` + 不同 WORKSPACE_ROOT），工作台打开时若 `/api/status` 的 workspaceRoot 与预期不符给出醒目提示；
  2. 高成本：多工作区支持（全局状态按工作区分片）——与现有取舍冲突，需要单独立项评估。
